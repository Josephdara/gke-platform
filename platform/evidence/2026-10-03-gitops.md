# GitOps deployment

This report records the first complete deployment path on GKE, from a [lab session](../../infra/README.md#sessions) on 2026-10-03: Argo CD bootstrapped on a fresh lab cluster, deploying staging from `main`, then a release and a rollback made only through pull requests. Times in the release and rollback table are elapsed from each merge. Values come from command output captured during the session; anything that was not captured is listed under [Deviations and gaps](#deviations-and-gaps).

Together, these results show the whole path working end to end: source, build, image digest, configuration pull request, Argo CD, healthy GKE service, and Git-based recovery.

## Release and rollback


| Step                                     | Release to B ([#7](https://github.com/Josephdara/gke-platform/pull/7)) | Rollback to A ([#8](https://github.com/Josephdara/gke-platform/pull/8)) |
| ---------------------------------------- | ----------------- | ------------------ |
| Merged (T0)                              | 0                 | 0                  |
| Argo CD started the sync                 | +1 min 14 s       | +1 min 44 s        |
| Argo CD finished the sync                | +1 min 16 s       | +1 min 45 s        |
| New ReplicaSet scaled 0 to 1             | +1 min 16 s       | +1 min 45 s        |
| Old ReplicaSet scaled 2 to 1, new 1 to 2 | +1 min 26 s       | +1 min 51 s        |
| Old ReplicaSet scaled 1 to 0 (T1)        | +1 min 37 s       | +1 min 57 s        |
| **Merge to healthy (T1 minus T0)**       | **1 min 37 s**    | **1 min 57 s**     |
| Of which, waiting for the next poll      | 74 s              | 104 s              |
| Of which, the rollout                    | 21 s              | 12 s               |


Sources: merge times from GitHub, sync times from the Application's deploy history, scaling times from Kubernetes ReplicaSet events. A watch loop sampling every 10 seconds independently saw the rollback reach `Synced/Healthy` with only release A running 1 min 59 s after the merge.

- **No unavailable pods:** each rollout added a new pod before removing an old one, so two pods stayed ready throughout. This is the chart's `maxSurge: 1`, `maxUnavailable: 0`.
- **No rebuild:** after both merges, the newest publish build was still the one for `62d0c72` (2026-10-02). The rollback pulled release A from the registry.
- **Final state:** a call from inside the cluster returned `200` and `{"service":"platform-verification-api","version":"sha-6d18354"}`.
- **Rollout speed:** the rollback's rollout was faster partly because release A's image was still cached on both nodes.



## Self-heal

Reported by the owner: the Deployment was scaled to 3 replicas by hand, and Argo CD returned it to 2 within about 10 seconds.

## Teardown

Reported by the owner: automated sync was turned off on both Applications, the lab was removed with a saved `lab_enabled=false` plan, and the inventory of clusters, instances, disks, addresses, forwarding rules, network endpoint groups, routers, networks, and firewall rules showed no lab resources left.

## Deviations and gaps


| Item                      | What happened                                                                                                                                  | Effect                                                                                                   |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| Release watch loop        | The first watch loop counted every pod in `staging`, including a test pod running release A's image, so it never reported release B on its own | Release timings were taken from the deploy history and ReplicaSet events instead, which are more precise |
| Availability probe        | A client meant to call the service every second during the release left no log                                                     | The no-downtime result rests on the ReplicaSet scaling sequence, not on client-side measurement          |
| Capacity before bootstrap | Only usage (`kubectl top nodes`) was recorded, not requested resources                                                                         | Requests are recorded after bootstrap only                                                               |
| Self-heal and teardown    | Command output was not recorded                                                                                                                | Results are as reported by the owner                                                                     |
| Check 5                   | Argo CD 3.5 does not log each Git fetch at the default log level                                                                               | Proven by the synced revision instead                                                                    |
| GKE version               | This cluster's node version was not recorded                                                                                                                                   | An earlier lab cluster ran `v1.36.4-gke.1247000`                                                               |




## Follow-ups

- Stop Markdown changes in the app folder from publishing images. Changed alongside this report: the publish trigger ignores `apps/platform-verification-api/**/*.md` once the Terraform change is applied.
- Add a PodDisruptionBudget and HPA to the chart, and the matching kinds to the `staging-services` project.
- Enforce Pod Security "restricted" on the `argocd` namespace, since the core install already meets it.
- Record node versions, self-heal output, and teardown output in future reports.
