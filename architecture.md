# GKE Application Platform Architecture

## Platform goal

The platform provides a reusable application deployment environment on GKE, built with Terraform, Kubernetes, Argo CD, Helm, Kyverno, VPC networking, Cloud Build, and Docker. It applies production engineering practices within a temporary staging environment. Reviewed configuration changes define application deployments.

LLM inference is a second workload class. Open models run on a dedicated, tainted node pool behind a retrieval augmented generation (RAG) assistant, and they go through the same Git review, Argo CD sync, admission policies, identity model, and evidence process as every other workload. The CPU stage serves Qwen2.5-1.5B-Instruct through llama.cpp; a GPU stage is planned later. See [Inference workload class](#inference-workload-class).

This document is the architecture source of truth. `plan.pdf` describes the platform's build sequencing and `inference-plan.pdf` the inference build's; validation reports record which requirements have been demonstrated.

## Resource ownership

- **Terraform** owns the required APIs, the VPC and subnets, Cloud Router and Cloud NAT, GKE cluster and node pools, the Artifact Registry image and mirror repositories, Secret Manager resources, IAM, and audit logging, Google service accounts, workload identity permissions, Cloud Build triggers and repository link, the build evidence bucket, the models bucket, the private DNS zone for Google APIs, and standalone DNS, IP, and certificate resources.
- **Argo CD** owns namespaces, scoped RBAC, Kubernetes service accounts (KSAs), application resources, SecretProviderClass, HPA/PDB, network policies, Gateway/HTTPRoute, and Kyverno.
- **Manual bootstrap** covers project and billing setup, one active Terraform state bucket and the APIs Terraform needs before it can run, the budget, the billing export dataset and its export configuration, the Cloud Build GitHub connection and its app installation, limited to this repository, the NS records that delegate the platform subdomain from the owner's Cloudflare-hosted domain, copying approved controller and model-serving images into the mirror repository, downloading and verifying model files and the RAG corpus and uploading them to the models bucket, Argo CD installation in each lab session, and secret values. These dependencies are documented for reproducibility.

Terraform and Argo CD have separate resource ownership boundaries. GKE controllers own the cloud resources generated from Gateway objects. Within Argo CD, the platform Application owns shared resources, including namespaces, namespace quotas and limits, default network policies, platform RBAC, AppProjects, service Application definitions, Gateway resources, and admission policies. Each service Application owns its service chart resources. An individual Kubernetes resource has only one Application owner.

## Project structure

The project resides in the personal organization’s K8s folder. GCP resource names follow `<environment>-<purpose>`, such as `staging-vpc`, because every resource is already scoped to the project; Google service accounts follow `<environment>-<service>-sa`. Names that must be globally unique, such as the Terraform state buckets, keep the `<project>-<environment>-<purpose>` form. Resources created before this convention keep their original names, including the image repository `gke-build-proj-staging-images`. Kubernetes resource names follow `<environment>-<service>`, such as `staging-platform-verification-api`, in one namespace per environment named `<environment>`, such as `staging`. A workload class that needs different quotas, limits, or node placement gets an additional namespace named `<environment>-<workload class>`; inference runs in `staging-inference`, and its workloads keep `<environment>-<service>` names, such as `staging-llm-cpu`. Supported resources carry `project`, `environment`, `service`, and `owner` labels; the project itself carries no labels, so cost grouping relies on resource labels.

## Region and zones

The cluster and workers reside in `us-east4-a`, within `us-east4`, which offers the machine types both inference stages use. The zonal topology accepts zone-wide outages for this temporary project. [GKE availability choices](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/configuration-overview).

## Budget controls and project lifecycle

The budget is $100, with owner notifications at 30%, 50%, and 99% of actual spend, counted before credits. The accounting period is monthly, in the billing account’s currency. The thresholds correspond to spending review, suspension of additional experiments, and an urgent spending alert. This alerts-only budget does not cap spending, and delayed usage reporting means the 99% alert cannot guarantee teardown before $100. Session duration, resource bounds, and owner-initiated teardown with spending headroom provide the cost controls. The budget and billing export configuration are managed manually in the console, so no billing account identifier appears in the repository; each lab session starts by confirming the budget still belongs to the project’s current billing account. The CPU inference stage is planned within this budget. [Budget behavior](https://docs.cloud.google.com/billing/docs/how-to/budgets).

Each lab session has a maximum lifecycle of 24 hours from creation to teardown. Persistent resources include the state bucket, enabled APIs, image repository and retained images, the mirror repository and its controller images, service accounts, Secret Manager secrets and retained versions, Cloud Build configuration, triggers, and GitHub connection, the build evidence bucket, the models bucket with its model files and corpus snapshots, billing export dataset, DNS zone, certificate resources and their DNS authorization records, and retained logs and evidence. Lab resources include the VPC and subnets, Cloud Router and Cloud NAT, the private DNS zone for Google APIs, cluster and node pools, including the inference CPU pool, controller-created load balancers, reserved endpoint IP, and service DNS A records. The endpoint IP and A record are recreated with the lab. Persistent storage and any other retained-resource charges remain part of the monthly budget. Teardown verification covers remaining load balancers, disks, IP addresses, registry storage, and retained data.

## Repository model

A single public repository contains `apps/`, `infra/`, `platform/`, and `pipeline/`. Cloud Build provides CI. Authorized branch pushes trigger validation. Protected main requires PRs and successful applicable checks from the trusted CI integration. Merges affecting application builds publish checked container images; reviewed deployment configuration selects the image digest that Argo CD reconciles. The repository must exclude secrets, personal account identifiers, Terraform state, and sensitive plan or build artifacts. [Branch protection](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches).

The delivery flow is application change, successful image build and scan, deployment configuration PR selecting the approved digest, Argo CD rendering from Git, and a healthy GKE deployment. A manual deployment configuration PR is sufficient. Chart, Application, AppProject, and pipeline changes receive platform-owner review because they can change deployment behavior or permissions.

## GKE cluster topology

The platform uses GKE Standard with DNS-based control-plane access, private nodes, the Secret Manager add-on, Cloud Logging, and Cloud Monitoring. The general-purpose node pool, `staging-super-pool`, has two `e2-standard-2` nodes and scales to four; it runs the controllers and every workload except the model servers. HPA, node auto-repair, and node auto-upgrade are enabled. GKE's kube state metrics cover Deployments, HPAs, Pods, and StatefulSets.

The inference CPU pool, `staging-infer-cpu-pool`, has `n2d-standard-4` nodes and scales from zero to two. Its taint and label `workload-class=llm-cpu` keep it for the CPU model server, one replica per node. N2D is used instead of E2 because E2 VMs can land on different CPU platforms, which makes per-replica benchmarks inconsistent; each benchmark records the node's CPU model. The pool upgrades with no surge and one unavailable node, so an upgrade never needs a third node. The cluster autoscaler owns node counts, and Terraform ignores them.

Tool and platform-controller versions are pinned to compatible stable releases. GKE follows the Regular release channel with managed automatic upgrades, so its version can change between experiments. The recorded tool, controller, and actual GKE versions form each experiment’s compatibility baseline. Capacity validation includes controller overhead on the initial two-node pool. [GKE release channels](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/release-channels).

## Networking

Terraform provisions a custom-mode VPC and subnet with node range `10.40.0.0/24`, pod range `10.41.0.0/20`, and service range `10.42.0.0/24`. Dataplane V2 provides network policy enforcement, and Private Google Access provides connectivity to Google services. During a lab session, a Cloud DNS private zone for `googleapis.com` resolves every Google API name to `private.googleapis.com` (199.36.153.8/30), so network policies can allow Google API egress by address range. The default internet gateway route stays in place, as Private Google Access requires. A Cloud Router and Cloud NAT give the private nodes and pods outbound access, used by Argo CD to read the repository from GitHub; they belong to the lab lifecycle and its cost accounting. Cloud NAT allows outbound connections without public node IPs or unsolicited inbound traffic, but it does not filter destinations. [Cloud NAT](https://docs.cloud.google.com/nat/docs/overview)

Application Services use ClusterIP. The first service is exposed through a global external managed Gateway, global static IP, DNS A record, and Certificate Manager certificate/map. Certificate DNS authorization allows certificate resources to remain independent of the temporary endpoint IP. Each public hostname has its own DNS authorization, managed certificate, and certificate map entry: `api.staging.gke.josephdara.com` for the verification service and `assistant.staging.gke.josephdara.com` for the RAG assistant. rag-api is the only inference component with a route. Argo CD owns Gateway resources; Terraform owns the standalone IP, DNS, and certificate resources. [Gateway TLS support](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/gateway-security), [certificate DNS authorization](https://docs.cloud.google.com/certificate-manager/docs/domain-authorization).

The DNS zone serves a subdomain of the owner's domain, which is registered with Cloudflare. NS records at Cloudflare delegate the subdomain to Cloud DNS, so Terraform manages the zone, the certificate's DNS authorization record, and the A record, and no Cloudflare credentials are used; the parent domain's CAA records, if any, must allow Google's certificate authority. The domain name appears in this repository, since it is public DNS information rather than an account identifier. Each environment has one HTTPS-only Gateway in its namespace, owned by the platform Application; a service attaches through an optional HTTPRoute, and its network policy then admits traffic only from Google's load-balancer proxy and health-check ranges.

Application namespaces deny all ingress and egress by default and allow DNS to cluster DNS. A service's ingress is opened only for approved callers, added with its first caller, the Gateway. Kubelet probes come from the Pod's own node, which network policy always allows. Workload connectivity includes DNS, approved service traffic, and identity or Google API access where required; mounted secrets need no workload egress because the node's CSI driver fetches them. Namespace isolation is part of the service interface.

In `staging`, a separate egress policy opens only the paths to inference: rag-api to the model servers, embeddings, and pgvector in `staging-inference`; and the load generator and a debug Job to the model servers, rag-api, `private.googleapis.com` on port 443, and the GKE metadata server at 169.254.169.254/32 on ports 80 and 8080. The load generator's path to the Gateway address is not in policy yet, because that address changes every lab session. `staging-inference` denies by default and allows DNS, ingress from approved callers and the Managed Prometheus collectors, and egress to the metadata server and `private.googleapis.com` only for Pods whose `service` label is on an approved list. Admission ties that label to the Pod's own KSA, so a Pod cannot claim another service's access. Model servers expose metrics on their serving port, so the collectors reach that port; this is accepted because the servers are internal-only, use no static keys, have read-only access to the models bucket, and accept no administrative calls.

Restrictive egress for platform controller namespaces is optional hardening. When enabled, it has explicit allowances for required DNS, Argo component communication, Kubernetes API access, GKE identity endpoints, and Google APIs; general outbound HTTPS is allowed for the Argo CD repository server to fetch Git sources.

Standard Kubernetes NetworkPolicy does not select destinations by domain name, so an internet HTTPS allowance limits which workloads connect, not the hosts they reach. GKE’s separate FQDN policy capability is outside the initial scope. Pod egress policies do not control node image pulls. Approved-registry admission rules limit application images to the image repository; in `staging-inference` they also accept the mirror repository, because serving images are third-party images the platform does not rebuild. Owner-managed controller images, currently Argo CD, Redis, and Kyverno, and the inference serving images are copied unchanged into a separate Artifact Registry mirror repository and pulled from it by digest; copying preserves each digest, and the mirror has no cleanup policy. `platform/mirror/images.yaml` lists each serving image with its source, digest, and purpose. Serving images are scanned with Trivy but not gated on the scan, so each material finding gets a recorded decision. Google-managed components are governed separately. [GKE network-policy requirements and capabilities](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/network-policy).

## Terraform

Infrastructure is one Terraform root organized into modules, with pinned stable Terraform/provider versions and a provider lock file. A restricted, versioned GCS bucket holds its single state independently of the infrastructure. Every operational plan explicitly sets `lab_enabled`. The variable defaults to `false`, so a plan that omits it proposes removing the lab; such a plan is discarded, never applied. Routine teardown applies a reviewed saved plan that disables the lab and removes only lab resources. Inference sessions also set `inference_cpu_enabled`, which creates the inference CPU pool and is rejected unless `lab_enabled` is true; `inference_min_nodes`, which defaults to zero, keeps inference nodes warm for scale-up tests.

Persistent resources have explicit deletion safeguards appropriate to the resource and provider. State records ownership. Provider deletion policies recorded in state block Terraform-initiated deletion even if the resource configuration is removed; Terraform lifecycle protection depends on the configuration remaining present. Neither prevents deletion outside Terraform, and resource removals or replacements require review. A routine teardown plan is acceptable only when it preserves the designated persistent resources. [Terraform lifecycle protection](https://developer.hashicorp.com/terraform/language/meta-arguments/lifecycle).

General PR validation performs static Terraform checks without state access. The owner creates and applies reviewed saved plans with the owner’s credentials; saved plans stay outside the repository because they may contain sensitive data. Terraform CI with a separate deployment identity is out of scope for this project.

## IAM and workload identity

Workload Identity Federation for GKE provides direct resource access with least-privilege permissions. Each service has its own KSA. Terraform grants that KSA's principal, identified by namespace and KSA name, access to individual Google Cloud resources, never to namespace-wide or pool-wide principal sets. Grants are kept in Terraform as maps from each resource to its readers, each a namespace and KSA, so one resource can serve several services across namespaces, such as a database password read in both `staging` and `staging-inference`. Model-server KSAs have `roles/storage.objectViewer` on the models bucket only. ingest reads only the `corpus/` prefix of the models bucket and writes only under `inference/ingest/` in the evidence bucket, each enforced by an IAM condition on the object name; it reads and writes objects by known path and never lists. The GKE metadata server prevents workloads from using the node's identity. Every cluster in the project shares one workload identity pool, so a KSA with the same namespace and name in another cluster would receive the same access; the project runs one cluster at a time. [Workload Identity Federation for GKE](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/workload-identity).

Deployment remains owner-operated, without separate break-glass access. CI and workload identities have permissions distinct from the owner’s organization-level access.

Validation builds have only the permissions needed for checks and their outputs, without image-publication, infrastructure-apply, application-secret, or Terraform-state access. Trusted publication builds use a separate identity with image-write access scoped to the image repository and access needed for build evidence. Validation builds run as `staging-build-validate-sa` with log writing only; publication builds run as `staging-build-publish-sa` with Artifact Registry write access scoped to the image repository, plus object creation on the evidence bucket. Because the repository is public, pull request builds from external contributors run only after an owner comment approves them. Infrastructure planning and applying are owner operations outside CI. Build triggers select the intended service account explicitly. [Cloud Build identities](https://docs.cloud.google.com/build/docs/securing-builds/configure-user-specified-service-accounts).

Node identities have Artifact Registry Reader access scoped to the image and mirror repositories and compatible node access scopes. Application KSA permissions govern application API calls independently of node image pulls. Argo CD reads the public Git repository without credentials. [GKE image access](https://docs.cloud.google.com/artifact-registry/docs/integrate-gke).

## Namespace isolation

Each environment has one namespace, plus one per workload class that needs its own quotas, limits, or node placement. Services in a namespace share it and are separated by their own KSA, resource-level grants, and network policies. Kubernetes RBAC cannot separate teams within a shared namespace; a team boundary requires its own namespace.

Developers have read-only access in their environment's namespaces to Pods, Pod logs, events, Deployments, Services, and ConfigMaps. They cannot read Secrets, exec into or port-forward to Pods, or change resources; deployment changes go through Git. A Role in each namespace grants this access to the Kubernetes group `staging-developers`. Group membership requires Google Groups for RBAC, and developers also need the IAM Kubernetes Engine Cluster Viewer role to obtain cluster credentials; until both are configured, access tests use impersonation. [Google Groups for RBAC](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/google-groups-rbac).

In `staging`, a ResourceQuota bounds the namespace at 2 CPU and 2Gi of requests, 4 CPU and 4Gi of limits, and 15 Pods, which fits rag-api and the load generator beside the verification service. A LimitRange supplies default requests of 50m CPU and 64Mi, default limits of 200m CPU and 128Mi, and a per-container maximum of 500m CPU and 256Mi.

In `staging-inference`, the quota is 8 CPU and 26Gi of requests, 10 CPU and 32Gi of limits, 12 Pods, 2 PersistentVolumeClaims, and 20Gi of storage. Its LimitRange supplies defaults of 100m CPU and 128Mi, ephemeral-storage defaults of a 128Mi request and a 1Gi limit, a per-container maximum of 4 CPU and 16Gi, and an ephemeral-storage maximum of 16Gi, which fits the model files in emptyDir volumes and stays below the 18.8 GB an inference node can allocate; a larger model raises it. The ephemeral-storage defaults are explicit because Kubernetes otherwise uses the maximum as the default, which would make every container without its own setting request the maximum. Quotas are revisited if more services are added.

## Secrets management

Secret Manager supplies mounted secrets through the managed GKE add-on. Each authorized KSA has `roles/secretmanager.secretAccessor` on the required secrets. pgvector has three: its superuser password, read only by pgvector, and one password for each application role, read by pgvector, which creates the role, and by the role's one service.

Automatic rotation is explicitly enabled on a supported GKE version with a two-minute rotation interval. Secret references intended to rotate resolve updated versions, and applications reread changed mounted files. Live validation measures the complete path from a new secret version to application use; the configured interval is not a guaranteed application-observation deadline. Secret values are seeded manually and excluded from Git, images, and Terraform inputs/state. [Managed add-on and rotation](https://docs.cloud.google.com/secret-manager/docs/secret-manager-managed-csi-component).

A service declares secrets in its environment values as `secrets[]` entries, each naming a Secret Manager secret and an environment variable ending in `_FILE`. The chart mounts each secret read-only in a chart-owned directory, resolves `versions/latest`, and passes only the file path through that variable. Applications that cannot load a valid secret at startup report not ready; after a rotation to an invalid value, they keep the last valid value and log only the error type. A bad secret therefore affects only the service that owns it and never takes down Pods already serving; recovery adds a corrected version before disabling the bad one. Data Access audit logs record which principal reads each secret version. The first service demonstrates the path with `staging-platform-verification-api-demo`, a JSON secret holding a label and a value; `staging-forbidden-demo` has no grants and is used only for refusal tests.

## Application services

The first service, `platform-verification-api`, uses Python with FastAPI and Uvicorn. It returns service/version JSON, plus its demo secret's label when one is configured, and exposes `/livez` for process health and `/readyz` for local initialization and required configuration. The inference work adds rag-api, an ingest job, and a load generator, described in [Inference workload class](#inference-workload-class).

JSON logs contain timestamp, severity, service, environment, release, request ID, status, and duration. Secret values remain internal to the applications and are never logged or returned.

## Helm chart design

A shared chart defines Deployment, ClusterIP Service, KSA, ConfigMap, secret mounts, and probes. The extended chart includes HPA, PDB, NetworkPolicy, and optional HTTPRoute. Model servers use a separate model-server chart, described in [Inference workload class](#inference-workload-class).

Required inputs are image digest, owner/cost labels, port, resource settings, and probe paths. Supported options include replica bounds through `replicas.min` and `replicas.max`, secret references through `secrets[]`, and an optional HTTPRoute to the environment's Gateway. The KSA is always `<environment>-<service>`. Schema and chart validation reject invalid types or ports, missing labels or digests, and inverted bounds. Arbitrary pod-spec overrides are outside the interface.

Security defaults include non-root execution, a read-only root filesystem, dropped capabilities, and disabled privilege escalation. Each application initially requests 100m CPU and 128Mi memory, with limits of 500m CPU and 256Mi memory. Replica bounds are two to three, CPU HPA targets 70%, and the PDB retains at least one available replica.

HPA is always on from chart version 1.0.0. It owns the live replica count within the declared bounds, and the rendered Deployment does not specify a competing fixed count for Argo CD to restore. [Argo CD and HPA ownership](https://argo-cd.readthedocs.io/en/stable/user-guide/best_practices/).

The chart's semantic version is the version of its configuration schema. A change that breaks existing values files raises the major version, and the platform README records what each version changed. Version 1.0.0 replaces `replicaCount` with replica bounds.

Rolling updates allow zero unavailable replicas and one surge replica. Probe defaults are five-second intervals, two-second timeouts, three consecutive failures, and a 30-second startup allowance. Graceful shutdown has a 30-second window by default. From chart version 1.2.0, the window and an optional preStop sleep are values, so rag-api can use 150 seconds with a 10-second preStop. The capacity model includes peak application replicas, rollout surge, and controller overhead.

Argo CD renders the chart from Git. Local validation and CI use one documented Helm baseline matching the pinned Argo CD release. Argo CD 3.5.3 bundles Helm 4.2.1, which is therefore the baseline. Render checks use the reviewed Git revision, matching values files and precedence, release name, namespace, fixed dependency versions, and relevant target Kubernetes capabilities. Matching Helm versions alone does not prove render equivalence or live deployment success. [Argo CD Helm inputs](https://argo-cd.readthedocs.io/en/stable/user-guide/helm/), [Application rendering options](https://argo-cd.readthedocs.io/en/stable/user-guide/application-specification/).

## Image build and software supply chain

An Artifact Registry repository in `us-east4` holds container images. Images are tagged `sha-<short commit>`, and tags are immutable, so a tag always names the same image. Build identities publish images and node identities pull them. Retention preserves deployed and designated recovery images, which are marked explicitly; other images become eligible for cleanup after seven days. Cleanup policies stay in dry-run mode until that marking exists and retention behavior has been verified. [Artifact Registry cleanup policies](https://docs.cloud.google.com/artifact-registry/docs/repositories/cleanup-policy).

Branch CI covers service tests, chart/schema checks, policy fixtures, and vulnerability scanning. Build records include the source commit, image digest, provenance, and SBOM. Fixable medium, high, or critical vulnerabilities block release unless an owner-approved exception records a reason and expiry. Images are scanned before publication, so a failed scan prevents the push. Cloud Build generates the provenance; the SBOM and scan report are stored in the persistent build evidence bucket for 90 days. The deletion rule matches only each application's build-evidence prefix, so inference evidence under `inference/` is kept, and a new application's prefix is added to the rule. Pull request builds run the service tests, the image build, the vulnerability scan, and the chart, Terraform, and policy checks. Signing enforcement is deferred.

Configuration PRs select existing image digests with successful build and required scan evidence tied to the source commit and exact digest. The owner verifies that evidence before opening the promotion PR, and PR checks validate the resulting configuration. Chart changes are reviewed as deployment changes because they affect every service using the chart. Image-build triggers cover application source, Dockerfiles, dependencies, and build configuration. Deployment-only changes receive their applicable validation without rebuilding an image. [Cloud Build trigger filtering](https://docs.cloud.google.com/build/docs/automating-builds/create-manage-triggers).

## GitOps and Argo CD

Argo CD is installed at a pinned version by a documented bootstrap at the start of each lab session, because the cluster is recreated every session. It uses the core installation, without the API server, web UI, or Dex, so nothing is exposed from the private cluster. The bootstrap applies Argo CD and its configuration from Git, then the root platform Application and its AppProject; the platform Application then owns the shared resources in its manifest source. The documented bootstrap remains part of the recovery design.

The application model consists of one platform Application, one Application per platform controller that Argo CD installs, currently Kyverno and the Custom Metrics Stackdriver Adapter, and one Application per service. A second root Application, `staging-profile`, applied by the bootstrap, syncs the active session-profile directory under `platform/profiles/`, which holds that profile's model-server Application. All use this Git repository on protected main. The platform Application reads a dedicated platform-manifest source separate from the service chart. Each service Application reads the shared chart in `platform/charts/service/` and its shared and staging values from `platform/services/`, with chart and values resolved from the same Git revision. Platform namespaces, CRDs, and other required prerequisites are ready before dependent service resources synchronize. [Application specification](https://argo-cd.readthedocs.io/en/stable/user-guide/application-specification/).

Argo CD renders the chart itself and polls the public repository without read credentials, so no public webhook endpoint is needed. Service AppProjects allow only the approved repository, service namespaces, local cluster, and required resource kinds. They exclude the Argo CD namespace and cluster-scoped resource management. The platform Application has the permissions required for shared and cluster-scoped resources. [AppProject restrictions](https://argo-cd.readthedocs.io/en/stable/user-guide/projects/).

Argo CD reconciles the latest desired configuration from protected main; intermediate commits may be skipped. Applications reconcile independently, so a repository revision does not imply an atomic rollout across services. Automated synchronization, self-healing, and bounded synchronization retries are enabled for all Applications; pruning is enabled for service Applications and `staging-profile` only, so a model-server Application removed from the active profile is deleted with its Deployment, HPA, and Pods, while removing a shared resource such as a namespace from Git does not delete it without owner action. Destructive platform changes require owner review. Argo CD synchronization and health status distinguish configuration drift from workload health; neither guarantees a successful release. Failed releases require correction or Git revert to retained configuration and image digests, without rebuilding the image. [Automated synchronization](https://argo-cd.readthedocs.io/en/stable/user-guide/auto_sync/).

Lab teardown follows the controller cleanup and persistent-resource requirements in Operations and recovery.

## Admission policy

Kyverno provides admission control under platform-owner responsibility. It is installed at a pinned version by its own Argo CD Application, from a Kustomize overlay of the upstream manifest that uses mirrored images, in a separate `platform-controllers` AppProject that allows the CRDs, cluster roles, and webhook configurations Kyverno needs. It synchronizes before namespace resources and services, uses server-side apply for its large CRDs, and Argo CD ignores the webhook fields Kyverno manages itself. Application policies select the designated application namespaces, `staging` and `staging-inference`, and workload kinds. They require approved registries, digest-pinned images, resource settings, ownership labels, approved KSAs, and restricted workload security; a workload's KSA must be `<environment>-<service>`, matching its labels, so no workload runs as another service's identity. Host namespaces and paths, privileged containers, added capabilities, and privilege escalation are prohibited for those application workloads. Two inference policies add model provenance, which requires model name and revision labels and a model SHA-256 annotation on model-server Pods, and inference bounds, which requires context and concurrency limits in the server arguments. Application policies fail closed: if Kyverno is unavailable, admission in application namespaces is refused, while system, Argo CD, and Kyverno namespaces are excluded so the platform can recover. Platform controllers and Google-managed components have separately reviewed policy coverage and required permissions. [Kyverno policy scope](https://kyverno.io/docs/policy-types/cluster-policy/match-exclude/).

Policies enter enforcement after an audit phase and successful positive/negative fixtures. Fixtures are workload controllers such as Deployments rather than bare Pods, because the LimitRange completes a Pod's missing resource settings before Kyverno validates it. CI and live isolation tests validate namespace and network requirements. No policy exceptions are used; any future exception must be resource-scoped, owner-approved, justified, and limited to 24 hours. Rejection messages identify the failed field and required correction.

## Observability

Cloud Logging retains application logs for 30 days, excluding secrets and sensitive payloads. Cloud Monitoring supplies infrastructure visibility, and Managed Service for Prometheus supplies request rate, error, and latency metrics. GKE's built-in Cloud Monitoring dashboards provide the platform views. One Terraform-defined inference dashboard adds requests and rejections, time to first token, retrieval time, queued and running requests per model server, generated tokens per second, replicas, and nodes per pool.

Email alerts notify the owner of zero ready replicas for two minutes, error rates above 1% for five minutes under traffic, or p95 latency above 500ms for five minutes. rag-api and the model servers are excluded from the latency and zero-ready-replica alerts, which would fire on normal LLM latency and on every model cold start. Inference alerts cover an unavailable model server, a RAG error rate above 5%, slow time to first token, a missing scaling metric, a failed ingest run, and an unavailable database. Prompts and answers never appear in logs, metrics, or alerts. A controlled failure validates notification delivery.

Active-test objectives for HTTP services are 99% successful requests and p95 latency below 500ms. Failed live acceptance checks place further releases on an owner-enforced hold until correction or recovery is verified. This hold is distinct from the automated checks required before a PR can merge. These objectives apply to experiments rather than a monthly production SLO.

## Cost allocation and showback

The four required labels provide ownership and allocation context, with `service` as the cost grouping. Schema validation and Kyverno enforce workload labels; CI validates infrastructure labels. GKE cost allocation and detailed billing export provide usage and billing data.

Each experiment has a cost report separating direct service costs from shared platform, idle, and unallocated costs. Initial estimates are reconciled with billing exports as data becomes available.

## Validation and evidence

Required PR checks cover the applicable service tests, container scanning, Helm rendering/schema validation with the documented Helm baseline, static Terraform validation, and positive/negative Kyverno fixtures. Approved-image evidence is checked by the owner when preparing a promotion PR. Infrastructure plans are created and applied by the owner from reviewed saved plans. Live checks cover deployment health, the running image digest matching approved configuration, secret refresh, authorized and unauthorized IAM/RBAC access, and namespace isolation. Live isolation checks include denied application egress; platform controller egress checks apply when that option is enabled. Retention checks confirm that deployed and recovery images remain available. Load, pod-failure, and node-drain exercises have separate execution paths.

## Developer onboarding

Onboarding prerequisites are repository access, documented tool versions, an approved image digest, service ownership, and verified permissions. CI provides configuration validation and feedback.

The developer interface consists of chart inputs and service registration submitted through a PR, without platform-source changes. Adding a service is documented, but not rehearsed in this project.

## Operations and recovery

The owner is responsible for health, spending, credentials, and component compatibility. Upgrade rehearsals and recorded version combinations support maintenance.

Incident diagnosis correlates release digest, Argo CD status, events, readiness, and logs. Persistent release-related health or acceptance failures are rollback conditions. Recovery authority remains with the owner.

Lab teardown prevents Argo CD from recreating resources being removed. Kubernetes deletion targets the owning Gateway and related resources, while the cluster and controllers required for finalization remain available. Controller-created load balancers and associated resources must finish cleanup before Terraform removes the cluster, network, and remaining lab resources. Deleting the cluster leaves dynamically provisioned disks behind, so the pgvector Application and its PersistentVolumeClaim are removed first, and the inventory check looks for leftover disks. Cleanup verification distinguishes expected persistent resources from leaked lab resources. [GKE Gateway cleanup risks](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/deploying-gateways).

Terraform, the Git repository, retained images, and documented bootstrap define cluster reconstruction. Protected state, secret versions, recovery images, and reports have independent retention. The applications are stateless except pgvector, whose single database is rebuilt by the ingest job each session. When a session's data is worth keeping, the `rag` schema is exported with `pg_dump` as `ingest` and restored into a fresh pgvector as its superuser, which keeps the tables' owner and `rag_api`'s grants. Initial recovery objectives are no loss of merged configuration and restoration within two hours, subject to access to retained dependencies.

## Inference workload class

The CPU stage serves Qwen2.5-1.5B-Instruct, quantized to Q4_K_M GGUF, through llama.cpp, behind a platform operations assistant that answers questions from the platform's own documents and a curated set of Kubernetes documentation pages. The GPU stage is described here when it starts.

| Component | Namespace | Node pool | Deployed with | Purpose |
| --- | --- | --- | --- | --- |
| rag-api | `staging` | General | Service chart | Sessions, retrieval, prompt assembly, limits, streaming, and the frontend |
| llm-cpu | `staging-inference` | Inference CPU | Model-server chart | llama.cpp serving the chat model |
| embeddings | `staging-inference` | General | Model-server chart | Text Embeddings Inference serving bge-small-en-v1.5 |
| pgvector | `staging-inference` | General | Kustomize manifests | Documents, chunks, vectors, and conversations |
| ingest | `staging-inference` | General | Suspended CronJob | Parses, chunks, embeds, and loads the corpus on demand |
| Metrics adapter | `custom-metrics` | General | Platform controllers Application | Exposes Managed Prometheus series to the HPA |
| Load generator | `staging` | General | Job | Benchmarks from a fixed location |

**Request path.** The browser reaches rag-api at `assistant.staging.gke.josephdara.com` through the existing Gateway, and rag-api serves the frontend and its API from that one origin. The user signs in with a password checked in constant time against a scrypt hash in a users file mounted from Secret Manager; attempts are limited per client address, read from the load balancer's `X-Forwarded-For`, and per username. rag-api sets a session cookie holding the username and an expiry, signed with HMAC-SHA256 and a key from Secret Manager, HttpOnly, Secure, SameSite=Strict, valid for 8 hours. Any replica can check it, and rotating the key revokes every session, since a single session cannot be revoked. State-changing requests also need a matching Origin header and a custom request header. Conversations are stored in pgvector for the signed-in user, history comes only from them, and each answer is saved with how it ended and its passages' text. Every response carries a Content Security Policy limited to the site's own scripts, styles, and API. For each question, rag-api embeds it through the embeddings service, runs an exact vector search in pgvector for the top five chunks, counts tokens with the model server's tokenizer, assembles a bounded prompt, and streams the answer from the model server's OpenAI-compatible endpoint as server-sent events. Citations in the answer are checked against the retrieved passages, and every stream ends with exactly one success, error, or cancelled event. Readiness checks only the rag-api process, so a dependency outage shows a clear message in the interface instead of removing rag-api from the load balancer.

**Session profile.** The CPU profile sets `inference_cpu_enabled`, which creates the inference CPU pool, and `staging-profile` syncs `platform/profiles/cpu/`, which holds the llm-cpu, pgvector, ingest, and rag-api Applications. ingest is a suspended CronJob pinned to one corpus revision, which a session starts once pgvector is ready. The profile requests 7.25 CPU and 9Gi in `staging-inference`.

**Model artifacts.** Model files live in the persistent bucket `gke-build-proj-staging-models`, with uniform bucket-level access, versioning, public access prevention, and a deletion safeguard. They are downloaded once on the owner's machine, checked against the published hashes, and uploaded. Each model has a manifest at `models/<name>.yaml` that records its name, source repository and revision, license, format and quantization, bucket path, every file's size and SHA-256, tokenizer and chat template source, and the context length the deployment allows. An init container, running a short standard-library script in a mirrored distroless Python image, copies the files into an emptyDir volume and verifies every size and SHA-256 before the server starts, so a Pod never becomes ready with the wrong model. Each replica downloads its own copy, which keeps replicas independent and makes cold-start time measurable.

**Data path.** The corpus is Markdown only: 25 Kubernetes documentation pages from `kubernetes/website` at a pinned commit, this repository's documentation at one commit, and two synthetic documents with embedded instructions for the injection tests. A snapshot and its manifest, which records each file's source, license, attribution, and SHA-256, are uploaded to `corpus/<revision>/` in the models bucket. ingest verifies each file, strips front matter and Hugo shortcodes, chunks at about 300 tokens with 40 of overlap inside one heading, measured with the embedding model's tokenizer, and embeds through the embeddings service. It is idempotent: an unchanged SHA-256 is skipped, a changed document's new revision is loaded and made active in one transaction, and a document no longer listed is retired with its chunks deleted. ingest owns the `rag` schema and applies its migrations; rag-api never changes the schema. pgvector creates two roles at first start: `ingest`, which owns the schema and corpus tables, and `rag_api`, which reads the corpus and writes only conversations and messages, so a compromised rag-api cannot alter what the model is grounded on. The database records the embedding model, revision, and dimensions, and rag-api refuses to retrieve when they differ from its own. Retrieval embeds the question with bge-small-en-v1.5's search instruction and keeps the top five chunks; a similarity floor, off at first, is tuned from the evaluation set.

**Model-server chart.** `platform/charts/model-server` deploys one model server, separate from the service chart, and its values schema rejects unknown keys. Every server has a two-replica ceiling, and context and concurrency limits and a default output length that the chart turns into server arguments. llama.cpp treats the output length as a default that a request can raise, up to its slot's context, so rag-api enforces the output limit. Rollouts use no surge and one unavailable replica, with required anti-affinity across nodes on the inference pool, so a release never asks for a third node. The Deployment has no replica count when autoscaling is on. The startup probe allows the model's download and load time, readiness passes only once the model is loaded, and liveness uses a long timeout so a busy server is not restarted. A preStop hook sleeps 10 seconds, so the Pod leaves the Service endpoints, then waits up to 120 more seconds until the server reports no requests in progress; the termination grace period is 150 seconds. Containers run as user 10001 with the RuntimeDefault seccomp profile, no capabilities, and a read-only root filesystem, with emptyDir volumes for model files, `/tmp`, and HOME.

**Autoscaling.** Managed Prometheus scrapes llm-cpu, and the Custom Metrics Stackdriver Adapter exposes `llamacpp:requests_deferred` and `llamacpp:requests_processing` as Pods metrics. The HPA scales llm-cpu from one to two replicas on their per-Pod averages, adding one Pod per 60 seconds and scaling down after a 300-second window; these are starting values for the tests. Anti-affinity means a second replica needs a second node, which the cluster autoscaler adds. The HPA owns replica counts and the cluster autoscaler owns node counts; neither Git nor Terraform sets them. A missing scaling metric is detected in two forms: no samples reaching Cloud Monitoring, and the HPA's ScalingActive condition turning false when the adapter fails.

**rag-api limits.** Each request allows 2,000 characters of input, 384 output tokens within a 4,096-token slot, and a 120-second deadline. Retrieved passages are capped at about 1,200 tokens of the slot, because prompt processing dominates the time to first token on CPU: a full-size request took 57 seconds in the first inference session, 36 of them before the first token. Each replica admits 3 concurrent generations, 6 across two replicas: more than one llm-cpu replica's 2 slots, so extra requests wait in the server's queue, which is the scaling signal, and fewer than the roughly 8 that two llm-cpu replicas can finish within the deadline. Above that limit rag-api returns 429 with Retry-After. The scaling experiments set the final value. The session rate limit is 10 requests per minute, counted per replica. The shutdown budget is a 130-second application shutdown, a 10-second preStop, and a 150-second termination grace period. A GCPBackendPolicy sets a 180-second backend timeout and 150-second connection draining, so streamed answers are not cut at the default 30 seconds, and a HealthCheckPolicy checks rag-api's readiness path. rag-api's keep-alive timeout is longer than the load balancer's 600 seconds. Its HTTP client to the model servers closes idle connections after 5 seconds, so requests spread across replicas.

**Evidence.** Every inference report records the Git revision, image digests, model manifest, server arguments, node machine type and CPU model, corpus revision, prompt set version, and load generator settings. Results are stated as measured in a controlled lab, naming the model, hardware, workload, and date. A fixed evaluation set of 30 questions scores retrieval and answers separately. The targets are 18 of 20 answerable questions retrieving a correct source in the top five, 16 of 20 producing a supported answer, no invented citations on the 5 questions the corpus cannot answer, and no adversarial question making the model follow instructions found in retrieved text. These are targets, not results.

The CPU stage is complete when the model servers deploy through Argo CD into `staging-inference` under every admission policy, Workload Identity grants pass allowed and denied tests, a signed-in user gets streamed, cited answers through the Gateway, scaling, cancellation, and failure tests have evidence, and the final evaluation is scored.
